# 09 — Visualization and UI

Status: design draft for review (2026-09-18). Decisions in ADR 0008 (recording and engine-to-UI protocol) and ADR 0009 (UI stack). Evidence from the UI research sheet is cited inline as [R9] with the underlying source.

## 1. Goals

1. Bird's-eye 2D view of any world with every actor moving smoothly, signals, RSUs with coverage, toggleable overlays, and time controls.
2. Click a vehicle in 2D and the camera flies down into a 3D chase, dashboard, or free-fly view of that vehicle with a HUD of its full OBU state (06-node-models §2.9) and live sparklines.
3. Inspector panels with a "why" tab for any value (provenance to model card and parameters).
4. Scenario editor with validation, presets, events timeline, and side-by-side comparison of runs.
5. Identical behaviour live and in replay, with sub-100 ms scrubbing.
6. Every UI action is a JSON-RPC method, so the copilot, notebooks, and CI can do what a human can.

## 2. Architecture

```
ui/
  packages/protocol   hand-written VWP layout types + client (WebSocket, keyframe/delta reader, JSON-RPC)
  packages/viewer     Three.js scene, world builder, instanced actors, overlays, cameras, HUD/sparkline widgets (framework-free)
  apps/studio         React 19 + TypeScript + Vite app: panels, config editor, inspector, plots, comparison, run browser
```

Data path (all binary, no JSON on the hot path):

```mermaid
flowchart LR
  E[Engine or replay reader<br/>VWP over WebSocket] --> W[Decoder Web Worker<br/>VWP frame → typed-array views]
  W -->|SharedArrayBuffer pose rings<br/>Atomics| V[Viewer (main thread or render worker)<br/>Three.js scene]
  W -->|postMessage transfer| S[Studio state (Zustand)<br/>events, telemetry, metrics]
  S --> P[uPlot sparklines · Plotly figures · inspector]
  V <-->|hit test, follow, overlay| S
```

- The decoder worker owns the socket (binaryType `arraybuffer`). VWP keyframes and deltas are a flat fixed layout, so there is no parse step at all: the worker reads the section offsets out of the frame prefix and wraps each pose column in a typed array over the received buffer (`new Int32Array(frame, off, n)`, VWP §9.4), then writes actor poses into double-buffered `SharedArrayBuffer` rings keyed by actor slot; the render loop samples the ring at its own cadence and interpolates between the two latest samples (the jevpilot idea of blending sampled shapes, applied to poses [R9: jevpilot `road-vectors.js`]).
- `SharedArrayBuffer` requires cross-origin isolation, so the engine's HTTP server (and the static WASM host) sends `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp` [R9: MDN SharedArrayBuffer]. Fallback without isolation: transfer `ArrayBuffer`s per delta (zero-copy `postMessage` transfer [R9: MDN postMessage]).
- Optional `OffscreenCanvas` render worker keeps the scene off the main thread when the app runs heavy plots [R9: MDN OffscreenCanvas].

## 3. One scene, two views

The 2D map and the 3D world are the same Three.js scene (ADR 0009). The 2D view is a top-down camera; the 3D view is a chase/dashboard/free-fly camera. The "click and fly down" interaction is therefore a camera path, not a scene switch, and every overlay exists in both views.

Camera model: a single `PerspectiveCamera` is used for both views. Top-down mode looks straight down (pitch 90°) from an altitude chosen so that the frustum covers the requested map extent; pan and zoom are altitude and target moves (`MapControls`-style [R9: three.js MapControls]). Because both views share one camera type, the transition is an interpolation of (position, target, field of view) with smooth damping (`camera-controls` `smoothDamp`/`fitToBox` [R9: camera-controls]), following jevpilot's exponential lerp for camera position and look target (`1 − exp(−4·dt)` and `1 − exp(−6·dt)` [R9: jevpilot `scene.js`]). An exact orthographic mode (`OrthographicCamera`) is available as a toggle for measurements and figure export; it disables the fly-down animation while active because Three.js does not interpolate projections.

Camera modes: `map` (top-down), `chase` (behind/above, orbit by drag), `dashboard` (driver's eye, yaw/pitch limited), `free` (fly), `rsu` (fixed at an RSU antenna), and `jump` to any node id. Jevpilot's mode set (`chase`, `map`, `hood`) and its `keepCameraOutsideBuildings` rule are the reference behaviours [R9: jevpilot `camera-input.js`].

## 4. Rendering plan and performance budget

Targets (ADR 0011): 60 fps with 5,000 rendered vehicles on an integrated GPU; 10,000 actors with off-screen aggregation; ≤ 100 ms seek.

| Element | Technique | Why |
|---|---|---|
| Vehicles, VRUs | one `InstancedMesh` per (class × LOD level); capacity preallocated, `count` set to the visible instances after CPU frustum culling; instances moved between LOD meshes by distance | measured on a Quest 2 integrated GPU: ~2,600 instances dropped 85 → 55 fps when all instances were always drawn; count-based culling plus per-LOD meshes "almost doubled" the frame rate [R9: vrmeup devlog]; the official `webgl_instancing_dynamic` example updates 10,000 instance matrices per frame [R9: three.js examples] |
| Building blocks | `BatchedMesh` (multi-draw) for extruded footprints, three LODs (box, box+roof, textured) | one draw for thousands of distinct geometries [R9: three.js BatchedMesh]; multi-draw is slower above ~100 k instances, which we never reach for buildings [R9: three.js discourse] |
| Roads and lane markings | merged static geometry per tile, unzoomed = one drawable per category, zoomed = per-tile drawables with quadtree culling | A/B Street's "GPU upload is expensive but redrawing cached geometry is cheap" pattern [R9: A/B Street docs] |
| Transmission pulses | instanced expanding rings with a shader time uniform; capacity 4,096 concurrent | GPU-side animation, no per-frame CPU work |
| Communication links | `LineSegments` with a preallocated buffer updated from the delta stream | thousands of segments in one draw |
| CBR heatmap, coverage | data texture on a ground plane (per-cell values from the engine's channel accounting), bilinear shader | no per-pixel CPU work; matches deck.gl's GPU aggregation idea without a second renderer [R9: deck.gl HeatmapLayer] |
| Labels | `CSS2DRenderer`, limited to the 64 nearest or selected nodes | DOM labels are per-element; the cap keeps cost bounded [R9: three.js CSS2DRenderer] |
| Picking | `three-mesh-bvh` raycast over instanced meshes | 500 rays against 80 k polygons at 60 fps in its demo [R9: three-mesh-bvh] |
| Off-screen actors | not instanced; aggregated per grid cell into the density/CBR textures and a count badge | 10,000-actor scenes never issue 10,000 instance updates |
| Pixel ratio | capped at 1.5, PCF shadows 2,048², ACES tone mapping, HDR sky | jevpilot's tested render profile on integrated GPUs [R9: jevpilot `render-profile.js`] |
| Renderer | `WebGLRenderer` now; `WebGPURenderer` behind a flag | vendors still describe WebGPU paths as maturing or not production-recommended [R9: deck.gl, PixiJS docs]; three.js falls back to WebGL 2 automatically [R9: three.js WebGPURenderer] |

Frame budget at 5,000 vehicles: pose sampling and matrix writes ~5,000 × (interpolate + compose) ≈ 1–2 ms in JS; instance buffer upload ≈ 320 KB (16 floats × 4 B × 5,000); buildings and roads are static; overlays are GPU-side. The remaining budget covers HUD updates (5 Hz for DOM, 20 Hz for sparklines).

Sparklines use uPlot (60 fps streaming at 10 % CPU for 3,600 points in its published benchmark [R9: uPlot README]). The inspector's "why" tab resolves each value's provenance id (02-architecture §6.5) into the model card, version, parameters and sources, and links to the generated model documentation. The same panel exists for RSUs, backend entities (queue depth, batch window, storage growth), links (latency, bytes), and the MA (open cases, decisions).

## 6. Studio panels

- **Run browser:** list of recordings and live runs with manifest summaries; open, compare, export.
- **Scenario editor:** generated from the JSON Schema (03-interfaces §13) with help text and units per field, presets, a world picker (OSM bbox, SUMO net, procedural, JSON, editor), validation with clickable errors, and an events timeline editor (drag events on a time axis; geofence drawing on the map).
- **Map editor:** draw lanes and junctions, place RSUs and cells, edit signal plans; writes the world JSON through the same importer path.
- **Overlays:** transmission pulses, links, CBR heatmap, coverage, revoked/attacker markers (ground-truth overlays are clearly labelled `GT` and can be locked off for blind evaluation), detection events, backend flows (animated dots on the backend topology panel), RSU/cell coverage, focus region boundary (02-architecture §7.3).
- **Time controls:** play, pause, step (one mobility step or one event), speed (0.1×–100×), scrub bar with event markers, jump to event.
- **Plots:** any metric vs time, distance, density, or config variable; per-node, per-class, network-wide; live (uPlot) and post-run (Plotly.js with SVG/PNG export [R9: plotly.js]); figure presets for the canonical research questions (08-measurement §7).
- **Comparison:** two to four runs side by side with synchronised time, difference overlays for metrics, and manifest diff.
- **Backend topology panel:** entities, links, queues, batch timers, CRL/CTL publication events.
- **Copilot panel:** chat that calls the same JSON-RPC methods (tool registry generated from the method list), showing each call and result.

## 7. Replay and seek

Recording is MCAP, with two channel encodings the reader must keep apart (ADR 0008; 12-build-decisions D11 item 5): the snapshot channels hold the VWP keyframe and delta frames verbatim, so replay hands the Studio the same bytes the live engine sent, while the event, telemetry and metric channels hold serde records bound for Parquet or JSONL and never reach the pose path. Seek: read the footer, summary offsets, chunk index, then the covering chunk's message index to the nearest keyframe ≤ t, then apply deltas up to t [R9: mcap.dev spec]. With a keyframe every 1 s of simulated time and deltas at the mobility step, a seek decodes at most one chunk and ≤ 10 deltas; keyframes hold quantised int16 mm poses on a per-keyframe origin, so a 10,000-actor keyframe is ≈ 100 KB before zstd. This is the video GOP pattern [R9: GOP], and the same "latest-at plus range" query split Rerun uses to keep scrubbing interactive [R9: Rerun primary query cache]. No published seek-latency numbers exist for MCAP viewers, so the ≤ 100 ms target is verified by a benchmark in CI (10-roadmap Phase 1 acceptance).

The replay reader is the same Rust code compiled natively (served by `v2xw serve --replay file.mcap`) or to WASM (static hosting), and emits the identical VWP stream, so the Studio has no replay-specific code path.

## 8. API parity (agent-friendly)

JSON-RPC 2.0 methods mirror UI actions one-to-one; the copilot's tool registry is generated from them, replacing the legacy 16-tool set (01-inventory §3.6) with a superset: `scenario.get/set/validate/save/load/list`, `world.import_osm/import_sumo/generate/edit`, `events.set`, `run.start/pause/step/seek/speed/stop`, `view.follow/camera/overlay`, `inspect.node/link/entity`, `explain(value_ref)`, `metrics.query/plot/export`, `experiment.define/run/status/compare`, `export.dataset/traces/telemetry`, `foundry.run`. Every method has a JSON Schema; the CLI and the Python API are generated from the same registry.

## 9. Packaging

Default: the engine serves the built Studio (`v2xw serve`) on localhost with the COOP/COEP headers. Static mode: the Studio plus the WASM engine/replay reader on any static host for tutorials and small scenarios (no backend). Desktop: an optional Tauri 2 shell later (Apache-2.0/MIT, ~600 KB, OS webview) with the caveat that webview engines differ per OS (WebView2, WKWebView, webkit2gtk) [R9: Tauri docs]; Electron is the fallback if webview parity becomes a problem.

## 10. Accessibility, theming, figures

Light and dark themes; colour-blind-safe categorical palette for actor states (benign, attacker, reported, revoked) with shape redundancy; keyboard control for time and camera; every plot exportable as SVG/PNG/CSV with the manifest hash stamped in the figure metadata.
