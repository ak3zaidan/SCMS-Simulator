### A.2 SUMO deep dive

| Item | Finding | Source |
|---|---|---|
| TraCI vs libsumo vs libtraci | **TraCI**: network-protocol client (any language) talking to a separate `sumo`/`sumo-gui` process over a socket — supports multiple simultaneous clients, works with sumo-gui. **Libsumo**: "the TraCI API as a C++ library" — same API surface exposed as static functions/wrapper classes linked directly into the client, eliminating "communication overhead due to the protocol and the socket communication"; native C++, pre-built bindings for Python (`pip install libsumo`), Java, C#, extensible via SWIG. Limitations: only **one simulation per process** (parallelism needs Python's `multiprocessing`), **cannot connect multiple clients**, sumo-gui under libsumo "does not work on Windows and is still highly experimental" elsewhere, stricter typing than TraCI (no implicit string→list/bool coercion), and subscriptions needing extra arguments are mostly unsupported (except `vehicle.getLeader`). **Libtraci**: a C++ TraCI *client* library, "fully API-compatible with libsumo", used when you need the GUI or multi-client support that libsumo can't give you. | https://sumo.dlr.de/docs/Libsumo.html (fetched 2026-09-18) |
| Determinism guarantees & caveats | Default RNG is **Mersenne Twister, seed 23423**; `--seed <INT>` pins it, `--random` deliberately breaks reproducibility (seeds from system time). SUMO runs "**multiple RNG instances to decouple different simulation aspects**" (vehicle loading, probabilistic flows, driving dynamics, devices) so that, e.g., loading extra vehicles doesn't perturb earlier vehicles' random draws — "all RNGs use the same seed" though, so the seed alone still fully determines the run. Official expectation: "all SUMO applications and tools are expected to produce the same results when running the same version repeatedly with the same arguments and inputs" across Windows/Linux/Mac. **Documented breakers of determinism** even with a fixed seed: (1) `--device.rerouting.threads` combined with `--weights.random-factor` (tracked as GitHub issue #10292); (2) coordinate-transform differences via the Proj library across platforms; (3) some models' internal logging path (EIDM, DriverState device, possibly Wiedemann/ToC) can perturb behavior. | https://sumo.dlr.de/docs/Simulation/Randomness.html (fetched 2026-09-18) |
| `--step-length` / step overhead | No published per-step wall-clock benchmark numbers were found in the fetched pages — **UNVERIFIED** as a number. (`--step-length` itself just sets the simulated seconds per internal step, default 1s; smaller values increase simulated-time resolution at a roughly proportional increase in wall-clock steps, but SUMO's own docs pages fetched here don't quantify this.) | — |
| netconvert OSM import features | `netconvert --osm file.xml`. Notable OSM-specific options (all confirmed present in the fetched netconvert reference, defaults noted): `--osm.sidewalks` (import sidewalks), `--osm.crossings` (import pedestrian crossings), `--osm.bike-access` (import/fix bike lanes), `--osm.lane-access` (lane-specific access restrictions), `--osm.turn-lanes` (import turn arrows from OSM to help connection-building), `--osm.elevation` / `--osm.layer-elevation` (elevation reconstruction from OSM `layer` tags, with a max-grade clamp), `--osm.all-attributes`/`--osm.extra-attributes` (import arbitrary extra OSM tags), `--tls.guess-signals` ("typical pattern for OSM-derived networks"), `--junctions.join` ("recommended for OSM import"), `--osm.oneway-spread-right`, `--osm.speedlimit-none` (default 39.44 m/s ≈ no-limit fallback), `--osm.railsignals`. | netconvert.md **[cache]**, lines ~505-524 (SUMO wiki `netconvert` page) |
| Pedestrian models | `--pedestrian.model` ∈ {`nonInteracting`, `striping` (default), `jupedsim`}. **striping**: lane divided into lateral "stripes" (`--pedestrian.striping.stripe-width`, default 0.65 m) for collision avoidance among pedestrians; has a "jammed" fallback state (default 300 s stuck → forced movement at 1/4 max speed, no collision registration while jammed; shorter 10 s timeout on crossings, 1 s on single-file-only elements) and configurable oncoming-traffic space reservation on junctions/crossings and (optionally) plain sidewalks. **jupedsim**: couples to **JuPedSim** (Jülich Research Center's social-force-model pedestrian simulator); "the coupling is a work in progress"; on Windows, JuPedSim ships bundled with the SUMO distribution, on Linux/macOS it must be built separately then SUMO rebuilt against it; geometry is expressed as extra polygons of type `jupedsim.walkable_area`/`jupedsim.obstacle`/`jupedsim.vanishing_area`/`jupedsim.influencer` in a SUMO "additional file"; pedestrians have a computed radius (half the max of vType length/width) and only one JuPedSim sub-model is currently exposed by SUMO. | pedestrians.md **[cache]**, lines 249-385 (SUMO wiki `Pedestrians` page) |
| OSM Web Wizard | Launched via `python osmWebWizard.py` from SUMO's `tools/` directory (or Start Menu on Windows). Lets a user pick a map area (or navigate/zoom to one), toggle imports (left-hand traffic, car-only, public transport, bicycles, pedestrians), and generates randomized demand for passenger cars, bicycles, pedestrians, motorcycles, buses, trucks, trams, trains and ships, then opens the scenario in sumo-gui. Documented caveats: large excerpts can make the simulation slow/unresponsive (recommends staying near the tool's default Berlin-view zoom level), importing more road types increases file size/complexity, and generated public-transport schedules are synthetic, not real timetables. | https://sumo.dlr.de/docs/Tutorials/OSMWebWizard.html (fetched 2026-09-18) |

### B.1 Cross-platform floating-point determinism

| Item | Finding | Source |
|---|---|---|
| IEEE 754 basic ops | Not independently re-verified by a fresh fetch this session (general IEEE 754 fact, not specific to any one vendor doc): basic ops (+,−,×,÷,√) are bit-reproducible across conforming implementations absent FMA contraction or "fast-math" reassociation. Rust's own docs (next row) explicitly confirm `sqrt()` is IEEE-754-guaranteed and unchanging. | doc.rust-lang.org f64 docs (below) |
| Rust: `sin`/`cos`/etc. are **not** guaranteed cross-platform | Rust's own std docs state, for `sin`, `cos`, `tan`, `asin`, `acos`, `atan`, `atan2`, `sinh`, `cosh`, `tanh`, `exp`, `exp2`, `ln`, `log`, `log2`, `log10`, `cbrt`, `hypot`, `pow`, etc.: **"Unspecified precision: The precision of this function is non-deterministic. This means it varies by platform, Rust version, and can even differ within the same execution from one invocation to the next."** `sin()` specifically: "This function currently corresponds to the `sin` from libc on Unix and Windows. Note that this might change in the future." I.e. **std transcendentals delegate to the platform libm** and give no cross-platform guarantee, confirming the brief's premise. | https://doc.rust-lang.org/std/primitive.f64.html (fetched 2026-09-18) |
| Rust: what **is** guaranteed | `sqrt()` — "guaranteed to be the rounded infinite-precision result... specified by IEEE 754 as `squareRoot` and guaranteed not to change." `mul_add()` (FMA) — likewise IEEE-754-guaranteed (`fusedMultiplyAdd`) and stable.
