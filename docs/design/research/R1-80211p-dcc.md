**Notes (Section A):**
- The FCC's 2020→2024 rulemaking (FCC 20-51 → FCC 24-123) completely replaced DSRC/802.11p with C-V2X as the mandated technology for the US 5.9 GHz ITS band; the DSRC/802.11p rules (§90.377, §95.3167/95.3189 referencing IEEE 802.11p‑2010) are retained only transitionally (sunset window specified in FCC 24-123 ¶¶ near line 1588). A simulator targeting *current* US deployments should model C-V2X (3GPP sidelink), not 802.11p; a simulator targeting *legacy* US DSRC or the *EU ITS-G5* market should use the 802.11p parameters in this sheet.
- There is an apparent tension inside FCC 24-123 itself between the RSU EIRP language in the body text (¶31, "we adopt a 33 dBm/10 MHz, 33 dBm/20 MHz, and 33 dBm/30 MHz EIRP PSD limit for C-V2X RSUs" — codified as new §90.391) and the *legacy* DSRC EIRP table retained under the amended §90.377(b) (23/33/40 dBm by channel). These are two different rules for two different technologies (C-V2X vs. legacy DSRC) coexisting during the transition window — not a contradiction, but easy to conflate; cite the specific CFR section (§90.377 vs §90.391) you mean.
- The "23 dBm EIRP for ITS-G5A" figure frequently quoted in secondary literature is EN 302 571's **PSD** limit (23 dBm/MHz), not a fixed total-power cap; the total-power cap is 33 dBm regardless of channel.

**Gap between model and measurement:** the NIST/ns-3 analytical model predicts 10% PER at 6 Mbps/400 B around **6.6 dB** SNR, while the Sjöberg et al. real-chipset lab measurement puts it around **11.5 dB** for a similarly-sized (300 B) frame — an approximately **5 dB** gap, attributable to non-ideal receiver implementation (channel estimation, synchronization, front-end losses) versus the model's ideal coherent-detection assumption. This gap is a useful calibration factor if the simulator's goal is to match real hardware rather than idealized 802.11a/g theory.

**Notes (Section C):** the NIST model in ns-3/Veins is a **clear-channel (no fading, no interference) AWGN** model — it produces the PER for a *given instantaneous SNR*; the vehicular channel's fading/shadowing (Abbas/Karedal-type models) determines what SNR trace is fed into it. A simulator combining both is doing the standard "path loss + shadowing + fast fading → instantaneous SNR → NIST/Yans PER lookup" pipeline used by ns-3 and Veins.

## D. ETSI DCC (TS 102 687, EN 302 571, TS 103 175)

### D.1 TS 102 687 adaptive approach parameters (clause 5.4, Table 3)

| Parameter | Value | Description |
|---|---|---|
| α | 0.016 | Algorithm (smoothing) parameter |
| β | 0.0012 | Algorithm (gain) parameter |
| CBRtarget | 0.68 | Target CBR that the adaptive loop drives toward |
| δmax | 0.03 | Upper bound on δ (max allowed medium-usage fraction), per EN 302 571 |
| δmin | 0.0006 | Lower bound on δ, prevents starvation at high CBR |
| Gmax⁺ | 0.0005 | Upper clamp on the per-step δ offset |
| Gmax⁻ | −0.00025 | Lower clamp on the per-step δ offset |
| TCBR | 100 ms | CBR measurement interval; δ itself is recomputed every 2×TCBR = 200 ms |

Source: ETSI TS 102 687 V1.2.1 (2018-04) clause 5.4, Table 3 — `txt/ts102687.txt` lines 316-345. **All values in the task brief were confirmed exactly as stated** (α=0.016, β=0.0012, CBRtarget=0.68, δmax=0.03, δmin=0.0006, Gmax⁺=0.0005, Gmax⁻=−0.00025).

Update algorithm (executed every 200 ms, i.e. when UTC mod 200 ms = 0):
1. `CBR_ITS-S = 0.5·CBR_ITS-S + 0.5·((CBR_L_0_Hop + CBR_L_0_Hop_Previous)/2)` (or the global CBR_G if TS 102 636-4-2 info-sharing is used)
2. `δ_offset = min(β·(CBRtarget − CBR_ITS-S), Gmax⁺)` if the sign is positive, else `max(β·(CBRtarget − CBR_ITS-S), Gmax⁻)`
3. `δ = (1−α)·δ + δ_offset`
4. Clamp δ to [δmin, δmax]

δ represents the max fraction of time the station may transmit; a gate-keeping function (informative Annex B) computes the next gate-open time `t_go = t_pg + min(max(Ton_pp/δ, 25 ms), 1 s)`. Source: `txt/ts102687.txt` lines 320-330, 430-460.

## What simulators do (cross-cutting summary)

- **PHY error model (§C):** ns-3 (and Veins, which ports the same code as `NistErrorRate.cc`) default to the **NIST/Pei-Henderson analytical AWGN model**, replacing the older, overly-optimistic Yans model. This model is clear-channel/AWGN only; realistic fading/shadowing (e.g. Abbas et al. LOS/OLOS/NLOS Markov model, Karedal et al. path-loss exponents) must be layered on top to produce the instantaneous SNR fed into the error-rate lookup. Real chipsets measured in the lab (Sjöberg et al.) require roughly **5 dB more SNR** than the ideal NIST model predicts for the same PER — a useful calibration offset if matching real 802.11p hardware (e.g., Cohda MK5) rather than idealized theory.
- **MAC/EDCA (§B):** ETSI's own reference document (EN 302 663 Annex C) **is** essentially a simulator-ready parameter sheet: aSlotTime=13 µs, aSIFSTime=32 µs, aCWmin/aCWmax=15/1023, plus per-AC AIFSN/CWmin/CWmax — these numbers can be dropped directly into ns-3's `WifiMac` or Veins' `Mac1609_4` EDCA queue configuration. Veins/`Mac1609_4` ships with ACKs disabled by default (`useAcks=false`) and RTS/CTS effectively disabled (`dot11RTSThreshold=12000 bit`, far above any BSM/CAM size), consistent with OCB broadcast operation. Neither ns-3 nor Veins implements a single fixed "capture threshold" constant the way older ns-2-based analytical models did (Torrent-Moreno et al., `CpTh`, ~5 dB SINR for 3 Mbps); modern packet-level simulators instead resolve capture implicitly through per-bit SINR trace evaluation against the chosen error-rate model.
- **CCA (§B.3):** ns-3's default OFDM `CcaEdThreshold` (−62 dBm) and `CcaSensitivity` (−82 dBm) and Veins' single `ccaThreshold` (−65 dBm) are all **simulator defaults for the general 802.11 PHY model**, not values pulled from the ETSI/802.11p vehicular-specific text — if a project needs standards-exact CCA behavior it should override these to match the ETSI CBR busy-threshold of −85 dBm (§A.6) for consistency with the ETSI DCC measurement definition, keeping in mind CCA-ED and the CBR "channel busy" threshold are conceptually related but not defined as the identical parameter in the standards.
- **DCC (§D):** No open-source simulator in this cache (ns-3, Veins) was found to ship a built-in, standards-conformant ETSI DCC_ACC/DCC_CROSS implementation as a default module — the TS 102 687 reactive/adaptive algorithms and the TS 103 175 `Toff_Limit` gatekeeper are typically implemented as custom application/MAC-layer add-ons on top of the base 802.11p MAC (e.g. via Veins' `DemoBaseApplLayer` scheduling, or ns-3 application-layer rate/power control), rather than being native to the PHY/MAC modules themselves.
- **Channel switching (§F):** Veins defaults to 1609.4-style CCH/SCH switching (`useServiceChannel=true`); an EU ITS-G5 study should generally set this to continuous CCH-only unless specifically modeling a multi-channel (SCH-using) European service, since real ITS-G5 deployments favor continuous single-channel or multi-transceiver operation over 1609.4 time-slicing.
- **SAE J2945/1 (§E):** the Rostami et al. paper's implementation was built specifically in a "calibrated ns-3 simulator" — i.e., this congestion-control algorithm's canonical simulator reference implementation already exists in ns-3 (used for the cited scalability studies), making it a good starting point over a from-scratch reimplementation.
