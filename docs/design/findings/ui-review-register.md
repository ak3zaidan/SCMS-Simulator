Two independent reviewers audited the Phase 1 UI: a wire-specification
conformance reviewer and a rendering/React quality reviewer. One critical

## Conformance verdict

SUBSTANTIALLY CONFORMANT ON LAYOUT, NOT YET INTEROPERABLE. Every byte offset, size, type and signedness in §2.1, all ten §3 prefixes, every struct-of-arrays column, the 208-byte §3.5.2 record, all 14 §3.6 event payloads, both §4 header/directory tables, all 32 §6.15 method names, the 8 §6.14 notifications and all 24 §6.4 error codes were checked field by field and match the spec exactly; the encoder reproduces the §9.1/§9.2/§9.3 hex dumps byte for byte and all 101 package tests pass. The decoder is also genuinely hardened: 34 of 35 crafted malformed frames (truncated body, body_len mismatch, unknown type, unknown version, bad/big-endian magic, zero actors, actor_count 0xFFFFFFFF, misaligned and out-of-range off_*, oversized counts, StrTable n=1e9) fail with a typed ProtocolError carrying the right close code, and bounds and alignment are checked before every typed-array view is constructed. BUT three disagreements will silently break the Rust engine: (1) Delta z is applied as centimetres while §3.2 defines dz_mm in millimetres — a 10x position error on every vertical delta, hidden because the package's own no_quantisation_drift test produces dz == 0 for all 10,000 steps; (2) the landuse class enum has water and park swapped against §4.5; (3) the world content-hash rule is ambiguous in the spec and the implementation's choice matches none of the three literal readings, so under §10.5 W1 the client would refuse every world. Findings 1 and 3 need a spec erratum agreed with the Rust implementer, not only a code change. Do not ship against an independently written engine until 1, 2, 3 and the resumed-Hello symbol-table reset (4) are settled.

## Specification conformance findings (S1..S14)

### S1 [CRITICAL] §3.2 (delta quantisation / delta reference rule), §3.4.2 (dz_mm)

**File.** /Users/ahmedzaidan/Developer/SCMS-Simulator/ui/packages/protocol/src/pose.ts (PoseBuffer.applyDelta, `this.zCm[s] += m.dzMm[i]`)

**Disagreement.** Delta z is applied as centimetres, not millimetres. §3.2 defines delta x/y/z as i16 MILLIMETRES against the previously transmitted quantised value; the keyframe/absolute reference for z is i16 CENTIMETRES (z_cm). The client adds the millimetre delta straight into the centimetre accumulator, a 10x error: with a keyframe z of 0.15 m, a dz_mm of +100 (0.10 m per §3.2) produced z = 1.15 m instead of 0.25 m (probe2.mjs). This is masked by the package's own Q2 test: test/quantisation.test.ts:126 and :154 build the producer side correctly in millimetres (`refZ = quantiseHeightCm(...) * 10`, `dz = qzMm - refZ`) and then assert the centimetre result, but the test trajectory z = 0.15 + 0.0031*sin(0.05t) quantises to z_cm = 15 at every one of the 10,001 steps, so dz_mm is identically 0 and `zCm += dzMm` is never exercised with a non-zero value (verified numerically: distinct z_cm values = [15], steps with dz != 0 = 0). The spec is itself self-inconsistent here — a field named dz_mm in millimetres whose reference field is z_cm in centimetres — so an independent Rust implementer writing the producer from §3.2 will emit millimetres and every vertical delta will be wrong by 10x, with no test on either side catching it.

**Fix.** Two-part. (a) Spec erratum, agreed with the Rust implementer, stating the z delta unit and reference unambiguously. Recommended: keep dz_mm in millimetres (it matches dx/dy and the 32,000 mm escape threshold) and state that the delta reference for z is the previously transmitted quantised value expressed in millimetres, i.e. z_cm*10. (b) Client change: keep the PoseBuffer z reference in millimetres (add a zMm column, derive zCm/positions from it, seed zMm = z_cm*10 from a keyframe and from the absolute block) so `zMm += dzMm` is dimensionally correct and the no-accumulated-drift guarantee of §3.2 holds on all three axes. Then change test/quantisation.test.ts to use a z trajectory with an amplitude of several centimetres so dz_mm is non-zero on most steps, and add a direct unit assertion (dz_mm = +100 must move z by exactly 0.100 m).

### S2 [HIGH] §4.5 (Landuse), Appendix A

**File.** /Users/ahmedzaidan/Developer/SCMS-Simulator/ui/packages/protocol/src/world.ts (LANDUSE_CLASSES)

**Disagreement.** The landuse class enum has values 4 and 5 swapped. Spec §4.5: `u8 class` @12 = 0 urban, 1 suburban, 2 rural, 3 highway, 4 water, 5 park, 6 industrial. Implementation: ["urban","suburban","rural","highway","park","water","industrial"]. Demonstrated end to end (probe4.mjs): a zone encoded with class_idx 4 (water) comes out of worldToJson as "park" and class_idx 5 (park) comes out as "water". Because worldFromJson uses LANDUSE_CLASSES.indexOf for the reverse mapping, the binary<->JSON parity test (§10.5 W4, test/world.test.ts:185) round-trips against the same wrong table and passes, so the error is invisible to the suite. §8.3 lists renumbering an enum as a MAJOR-breaking change, so this is exactly the class of divergence that makes the JSON mirror and the Rust importer disagree.

**Fix.** Swap the two entries: `export const LANDUSE_CLASSES = ["urban", "suburban", "rural", "highway", "water", "park", "industrial"] as const;` and add a test that asserts each numeric index against the §4.5 names rather than only round-tripping.

### S3 [HIGH] §4.2 (content_hash), §3.9 (WorldChunk verification), §10.5 W1/W3

**File.** /Users/ahmedzaidan/Developer/SCMS-Simulator/ui/packages/protocol/src/world.ts (computeWorldContentHash, computeWorldContentHashWith) and .../src/encode.ts (encodeWorld)

**Disagreement.** The world content-hash rule is ambiguous in the spec and the implementation's choice matches none of the literal readings, so the client and the Rust engine will compute different world hashes. §4.2 says content_hash is "SHA-256 of the body" while storing it inside the body at offset 0 (self-referential, impossible as written); §10.5 W1 says `GET /world/{hash}.vwb` returns "a body whose SHA-256 equals {hash} and Hello.world_hash", which reads as the whole served file including the 16-byte header; §3.9 says the client MUST verify SHA-256(concat(WorldChunk payloads)) == world_hash, again the whole file. The implementation picks a fourth rule — SHA-256 of the vwb body with the 32-byte content_hash field zeroed — and documents the ambiguity in a comment. All four digests differ for the same file (probe4.mjs): stored/impl d53c25fb…, whole file 2b50e905…, body-as-stored 1b5dacdb…, body[32..] c45d5549…. If the Rust side implements W1 (the most natural reading for a content-addressed URL), Hello.world_hash will never equal what the client computes and, per W3, a conforming client refuses every world.

**Fix.** Pin one rule in the spec and implement it. Recommended: define `world_hash` = SHA-256 of the exact bytes served at /world/{hash}.vwb (header included), used for the URL, Hello.world_hash and the §3.9 chunk check; keep the in-body `content_hash` as an informational copy, explicitly defined as SHA-256 of the body with its own 32 bytes zeroed; state both in §4.2, §3.9 and §10.5 W1 so neither side has to guess. Then add a client helper that hashes the served bytes and compares against Hello.world_hash, and wire it into the world-load path so W3 is actually satisfied.

### S4 [MEDIUM] §1.4 case 1 (resume), §2.5 (symbol table), §10.4 C7

**File.** /Users/ahmedzaidan/Developer/SCMS-Simulator/ui/packages/protocol/src/client.ts (VwpClient.#route, the "hello" case)

**Disagreement.** A resumed Hello resets the symbol table. §1.4 case 1 says on a successful resume "the client keeps its world, string table, actor slots and camera state", and §2.5 says only "a non-resumed Hello resets the table" and that ids are never reassigned within a connection. The code calls `this.strings.reset(msg.strings)` in BOTH the resumed and the non-resumed branch, truncating the table to the n ids the Hello re-establishes and discarding every id a previous Provenance frame appended. Reproduced (probe3.mjs): table size 3 after the first Hello, 5 after a Provenance appends two strings, back to 3 after a HELLO_RESUMED Hello, with ids 3 and 4 now resolving to "". Every subsequent MetricSample.str_metric, Provenance.str_model_id or event str_* pointing at an id >= n renders blank until the server happens to resend a Provenance frame — and if the server keeps counting from its own (larger) table size, the client's later appends land at the wrong global ids and all strings shift. The two existing tests (test/messages.test.ts:71, test/client.test.ts:186) only cover the non-resumed case.

**Fix.** In the `resumed` branch, do not reset: leave the table as it is (optionally assert that the first msg.strings.length entries match what is already held, and emit a protocol error if they do not). Keep `strings.reset(msg.strings)` for the non-resumed branch only. Add a test that appends via Provenance, delivers a HELLO_RESUMED Hello and asserts the appended ids survive.

### S5 [MEDIUM] §3.6.1 (skip unknown channels by payload_len), §3.6.4–§3.6.17 (fixed record sizes)

**File.** /Users/ahmedzaidan/Developer/SCMS-Simulator/ui/packages/protocol/src/messages.ts (decodeEventPayload, digest8)

**Disagreement.** decodeEventPayload reads fixed offsets without checking the payload is long enough, and digest8 escapes the DataView bounds entirely. A malformed payload_len shorter than the channel's record (e.g. 8 for phy.rx, which needs 48) throws a bare RangeError, not a ProtocolError, so VwpClient.handleBinaryFrame's `err instanceof ProtocolError` branch does not fire and the error propagates out of the message handler instead of closing the socket with 1002 — the "confusing error" case, and the only untyped failure among 35 malformed-frame probes. Separately, `digest8(dv, off)` returns `new Uint8Array(dv.buffer, dv.byteOffset + off, 8)`, which is bounded by the underlying ArrayBuffer rather than by the declared payload: with a 30-byte node.tx payload it read bytes 28..36, i.e. 6 bytes of the neighbouring payload, and returned them as pseudonym_digest before a later field threw (probe2.mjs printed the 0x11-filled bytes read from outside the 30-byte view). That is a real out-of-bounds read relative to the wire structure and it would silently corrupt a HashedId8 rather than reject the frame.

**Fix.** Add a per-channel minimum record size (40 node.tx, 48 phy.rx, 48 node.verify, 40 sec.cert, 32 det.observation, 32 app.warning, 32 proto.revocation, 56 gt.kinematics, 32 gt.attack.action, 16 mac.cbr, 24 net.frag, 32 node.neighbor, 32 proto.msg, 40 ma.*) and, at the top of decodeEventPayload, throw `new ProtocolError("bad_length", …, { field: channel })` when `dv.byteLength` is below it — unknown channels keep falling through to UnknownPayload as today. Change digest8 to clamp: `const n = Math.max(0, Math.min(8, dv.byteLength - off))` and view only that many bytes (or throw if n < 8).

### S6 [MEDIUM] §2.2 (`off_* = 0` means section absent), §3.1

**File.** /Users/ahmedzaidan/Developer/SCMS-Simulator/ui/packages/protocol/src/messages.ts (decodeHello)

**Disagreement.** decodeHello does not honour the `off_* == 0` "section absent" sentinel, unlike every other decoder in the file. decodeKeyframe, decodeDelta, decodeEvent, decodeProvenance and decodeSignalBlock all guard with `count === 0 || off === 0`; decodeHello indexes unconditionally from offNodes/offClasses/offChannels/offWorldRef. With node_count = 1 and off_nodes = 0 the node table is built over the Hello PREFIX and the decoder reports nodes.count = 1 with node_id[0] = 1 — which is the u32 formed by version_major=1 and version_minor=0 (probe.mjs). No error is raised, so a malformed or half-written Hello yields plausible-looking garbage node, class and channel tables instead of a clean rejection.

**Fix.** In decodeHello, resolve each table as: count 0 -> empty table; count > 0 and off == 0 -> `throw new ProtocolError("bad_offset", "Hello.nodes: node_count is N but off_nodes is 0 (§2.2 section-absent sentinel)")`; otherwise decode as now. Same for classes, channels and world_ref (whose off is never legitimately 0 since §3.1 always includes it).

### S7 [MEDIUM] §3.4 (a Delta is meaningful only against its own GOP; deltas are never partially applied), §1.5

**File.** /Users/ahmedzaidan/Developer/SCMS-Simulator/ui/packages/protocol/src/pose.ts (PoseBuffer.applyDelta)

**Disagreement.** applyDelta is not all-or-nothing, contradicting both its own docstring ("Refused — without mutating anything —") and the §1.5/§3.4 rationale that a partially applied delta leaves the pose ring against the wrong base. The gop/step/keyframe preconditions are checked up front, but the per-row consistency checks are not: a moved row with MFLAG_LANE_CHANGED and an empty lane block, MFLAG_ABSOLUTE and an empty absolute block, or a slot beyond capacity all throw ProtocolError("bad_state") from inside the loop, after earlier rows (and, in the same row, the position update) have already been written. Reproduced (probe2.mjs): with one moved row carrying LANE_CHANGED and no lane block, x_mm had already advanced from 512345 to 512346 when the throw landed, and #stepIndex was left un-advanced — so the buffer is now a state that neither the keyframe nor the keyframe-plus-delta describes, and the next delta is applied on top of it.

**Fix.** Validate before mutating: count the ABSOLUTE and LANE_CHANGED bits across m.mflags and require `d.absolute.count >= absNeeded` and `d.lanes.length >= laneNeeded`; check `max(m.slot[i], sp.slot[i]) < bound` in the same pre-pass; only then run the apply loops. Alternatively stage the touched slots into a scratch buffer and commit on success. Either way the throw must leave the buffer exactly as the previous frame left it, and the docstring's promise then holds.

### S8 [MEDIUM] §3.4.5 (spawn slot), §3.1.1 (actor_capacity is a preallocation hint)

**File.** /Users/ahmedzaidan/Developer/SCMS-Simulator/ui/packages/protocol/src/pose.ts (applyDelta spawn loop -> ensureCapacity) and .../src/slots.ts (SlotTable.adoptSpawn -> ensureCapacity)

**Disagreement.** An untrusted slot id from the wire drives unbounded allocation. VwpClient clamps the Hello-driven growth to 1<<20 slots, but a Delta spawn row's `slot` is passed straight to `ensureCapacity(slot + 1)`, whose doubling loop then allocates 14 typed-array columns plus a 3-wide Float32Array of positions. A single malformed delta with slot = 3,000,000,000 grew the PoseBuffer to capacity 4,294,967,296 and returned applied = true with no error (probe2.mjs) — about 116 GB of typed arrays, i.e. a trivial memory-exhaustion / hang vector from one frame, and the same path exists in SlotTable.adoptSpawn. Nothing in the spec suggests a client should honour a slot id larger than actor_capacity.

**Fix.** Derive a hard bound at Hello time (e.g. `max(Hello.actor_capacity, initial capacity)` with the same 1<<20 ceiling the client already applies) and reject a spawn or moved row whose slot is at or above it with `ProtocolError("bad_offset", "Delta spawns slot S exceeds the actor capacity bound")` before any allocation, in both PoseBuffer and SlotTable.

### S9 [LOW] §3.6.1 (off_index/off_payloads MUST be 8-aligned; payload_off MUST be a multiple of 8; index sorted by (sim_time_ns, channel_id)), §10.4 C4

**File.** /Users/ahmedzaidan/Developer/SCMS-Simulator/ui/packages/protocol/src/messages.ts (decodeEvent)

**Disagreement.** The reader does not verify three §3.6.1 MUSTs that the writer honours. off_index gets an implicit 8-alignment check (the u64s helper asserts it for sim_time_ns), but off_payloads is never checked for 8-alignment, each entry's payload_off is never checked for `% 8 == 0`, and the index is never checked to be sorted by (sim_time_ns, channel_id). encodeEventBody does all three correctly and test/messages.test.ts:189 asserts them on the encoder, so a non-conforming producer would be accepted silently and the misalignment would only show up later as a mis-decoded f32/u64 inside a payload.

**Fix.** In decodeEvent, assert `offPayloads % 8 === 0` via the existing align() helper, assert `index.payloadOff[i] % 8 === 0` in payloadView, and either assert the (sim_time_ns, channel_id) ordering once per frame or document explicitly that the reader trusts it (C4 is a `B` item, so the reader side should be checked).

### S10 [LOW] §2.5 (offsets[0] = 0, offsets[n] = blob_bytes, non-decreasing)

**File.** /Users/ahmedzaidan/Developer/SCMS-Simulator/ui/packages/protocol/src/messages.ts (decodeStrTable, strTableStrings)

**Disagreement.** Two of the three StrTable invariants are only enforced indirectly. strTableStrings rejects non-monotonic offsets and any offset beyond blob_bytes, which catches offsets[0] != 0 and a too-small offsets[n] in the common cases I probed (both were rejected with bad_offset). But the endpoints are never asserted directly, so a monotonic table with offsets[n] = blob_bytes - 1 is accepted and silently truncates the last string by a byte, and a table whose offsets[0] > 0 with everything shifted consistently would drop the first bytes of the blob without complaint. decodeStrTable also bounds the table against `buffer.byteLength` rather than against the enclosing body end, so for an uncompressed frame with trailing bytes a table can legitimately read a few bytes past body_len.

**Fix.** Assert `offsets[0] === 0` and `offsets[count] === blobBytes` in decodeStrTable, and pass the body end (bodyOffset + bodyLen) in as the bound instead of buffer.byteLength.

### S11 [LOW] §2.5 (only Provenance appends), §3.10, §3.11

**File.** /Users/ahmedzaidan/Developer/SCMS-Simulator/ui/packages/protocol/src/messages.ts (decodeError, decodeBye) and .../src/client.ts (#route, the "error" and "bye" cases)

**Disagreement.** Whether an Error or Bye symbol-table extension consumes connection string ids is undefined, and the implementation has guessed. §2.5 names only Provenance as appending to the per-connection table, yet §3.10 and §3.11 both end in "a symbol-table extension". The implementation assumes it does consume ids: decodeError computes `base = table.size` and resolves ids >= base out of the frame's own table, client.ts then appends the extension to the connection table, and encodeErrorBody takes an explicit `firstStringId` parameter. If the Rust server instead numbers an Error's strings locally from 0 (the other reasonable reading), str_message resolves to a stale connection string; and if the server does not count them as consuming global ids while the client does, the client's table is inflated and every later Provenance append lands at the wrong global id, shifting all subsequent string resolution. The `firstStringId` parameter shows the implementer saw the gap.

**Fix.** State the rule in §2.5 explicitly — recommended: Error and Bye extensions DO append to the per-connection table exactly as Provenance does, with the first entry taking id = current table size, which is what this implementation assumes — and add it to the Appendix C decision log so the Rust side cannot read it the other way.

### S12 [INFO] §10.1 F4 (all integers and floats are little-endian; a big-endian host produces identical bytes), §2.2

**File.** /Users/ahmedzaidan/Developer/SCMS-Simulator/ui/packages/protocol/src/messages.ts, src/frame.ts, src/world.ts

**Disagreement.** Explicit endianness is perfect but the zero-copy path is host-endian. Every one of the 575 multi-byte DataView accesses across the package passes littleEndian = true — a grep for a multi-byte get/set without `true` returns nothing, in frame.ts, messages.ts, encode.ts, world.ts and worker.ts alike. However the whole point of §2.2 is that the pose columns are read as `new Int32Array(buffer, off, n)`, and typed-array views use the HOST byte order, so on a big-endian host every pose column, signal id, lane id and telemetry raw region would be byte-swapped while the DataView-read prefixes stayed correct. The spec's own §9.4 TypeScript reference decoder has exactly the same property, so this is an accepted consequence of the zero-parse design rather than a bug — but F4's literal wording holds only for the encoder path, and nothing in the package detects the situation.

**Fix.** No code change needed for correctness on any realistic target. Either add a one-time module-load assertion that the host is little-endian (`new Uint8Array(new Uint32Array([1]).buffer)[0] === 1`) and throw a clear error otherwise, or add a sentence to §2.2 saying the zero-copy typed-array path requires a little-endian host and that F4 is a statement about the bytes on the wire, not about view construction.

### S13 [INFO] §1.3 rule 1 (Hello MUST NOT be compressed), §10.1 F7

**File.** /Users/ahmedzaidan/Developer/SCMS-Simulator/ui/packages/protocol/src/encode.ts (helloFrame) and .../src/messages.ts (viewFrame)

**Disagreement.** Nothing enforces that Hello is never compressed. `helloFrame(init, seq, flags = 0)` accepts an arbitrary flags word, so a caller (the mock engine server that these encoders exist for) can set FLAG_COMPRESSED on a Hello whose body is not in fact a zstd frame, and viewFrame will happily try to decompress it — or reject it as compressed_unsupported on a compress=none client, which is the failure mode §1.3 rule 1 exists to prevent. F7 is an `S` item, and this package is the writer for the mock server, so the hole is reachable.

**Fix.** Mask FLAG_COMPRESSED out in helloFrame (or drop its flags argument entirely, since §1.3 fixes the only flags a Hello may carry), and have viewFrame reject `msgType === MsgType.Hello && (flags & COMPRESSED)` with ProtocolError("bad_state").

### Q1 [HIGH] `/Users/ahmedzaidan/Developer/SCMS-Simulator/ui/packages/viewer/src/interp.ts`:301

**Problem.** Pose interpolation is keyed entirely off *arrival* wall-clock time, not sim time. `capture()` records `s.simSeconds = Number(poses.simTimeNs)/1e9` (line 280) but `sample()` never reads it — grep confirms `simSeconds` appears only at interp.ts:27, :89 and :280 and nowhere else in the package.
